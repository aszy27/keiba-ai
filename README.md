# 🏇 Keiba AI Prediction System

JRA の中央競馬を対象に、「市場（オッズ）が見落としている情報があるか」を検証しているプロジェクトです。
オッズを出発点にして、**オッズに含まれていない分だけを学習する単勝モデル**を作り、事前登録した検証で確かめています。

> **現在の到達点（2026-10-02）**: 過去8年の前進検証では、確定オッズに対して小さいながら一貫した上積みがあります。
> ただし**実際に買える時点（発走前）のオッズでの検証がまだ終わっていないため、実際には賭けていません。**
> 2つの候補（C[all]・候補2）を事前登録済みで、発走前オッズのスナップショットが1,000レースたまった時点（2027年1月ごろの見込み）で、候補ごとに1回だけ判定します。

## 考え方

着順を当てるモデル（旧システム、下の「旧システム（v1）」）は、的中率は出ても回収率は市場（人気）とほぼ同じでした。
モデルの評価が人気とほぼ同じなら、控除率の分だけ負けます。そこで発想を変え、**オッズを出発点にして、オッズに含まれていない分だけを学習**します（Benter 1994 と同じ2段階の構成）。

```
[段階1] 基礎モデル（オッズを使わない LightGBM、1〜3着の順序で学習）→ 各馬の勝率
[段階2] log(勝率) = a·log(オッズ由来の勝率) + b·log(基礎モデルの勝率) + 残差 LightGBM
        期待値（勝率 × オッズ）が閾値以上の単勝を買う
```
* 評価の指標は的中率ではなく、**勝ち馬の対数尤度が「オッズのみ」のモデルよりどれだけ良いか（C − A）**と、事前に決めた期待値の閾値での回収率です。
* 特徴量は 176列（能力・適性・近況・騎手/調教師・血統・展開・不利・当日の馬場傾向など）。
  学習・検証・本番で同じ関数（`prep/features.py`）を使い、「未来や当日の結果を消しても特徴量が変わらない」ことをテストで確認しています。

### 検証の進め方
過去の数字を見ながら設計を直すと、その期間の成績は必ず良く見えます（旧システムはこれで回収率を過大評価しました）。
そのため、**判定に使う期間・候補・閾値・合格の条件を、結果を見る前に `docs/rebuild_plan.md` に記録してから1回だけ実行**しています。
不合格になった候補を同じ期間で差し替えることはしません。多くの技術を試すときは、2019〜2022年で選び、2023〜2026年で確かめる2段階にしています。

## 結果

### 前進検証（2019〜2026-09-06、26,468R、確定オッズ）
| 版 | C − A（1レースあたり） | 2026年 | 期待値ベースの単勝 |
|---|---|---|---|
| C[all]（2026-09-17 登録） | +0.0132 [+0.0108, +0.0156] | −0.0007 | 1.2以上 14,604点・120.5% |
| **候補2（2026-10-01 登録）** | **+0.0186 [+0.0161, +0.0210]** | +0.0060 | **1.3以上 5,126点・136.8% [117.1, 160.5]** |

* 候補2は C[all] より 8年すべてで良く、差は +0.0055 [+0.0044, +0.0066]。期待値1.3以上の単勝は 8年すべてで100%超でした。
* **ただしこれは楽観的な数字です。** 確定オッズで買うかどうかを決めている（締切直前のオッズの動きを後から使えてしまう）うえ、何度も見た期間です。
  的中率7%・平均37倍の穴馬中心なので、1,000R 程度では実力があっても赤字になりえます。
* 効いたのは学習と結合の技術（1〜3着の順序で学習・残差の学習期間を広げる・残差にオッズ列・種類の違う版の単純平均）。
  特徴量の追加（第5〜7弾）と、15の技術のうち14（温度補正・ハイパーパラメータ探索・Shin の確率・ドメイン適応の重みなど）は効きませんでした。
  経緯は `docs/rebuild_plan.md`、論文の形の整理は `docs/paper_draft.md`。

### 前向き検証（事前登録済み・判定待ち）
| | C[all] | 候補2 |
|---|---|---|
| モデル | 基礎（1着で学習）＋残差1つ | 基礎（1〜3着で学習）＋残差4版の対数プーリング |
| 買い方 | 期待値1.2以上の単勝 | 期待値1.3以上の単勝 |
| 対象 | 2026-09-07 以降（実際はスナップショットの取得開始から） | 2026-10-02 以降 |
| 合格の条件 | C − A の95%下限 > 0、回収率 > 100% | C − A の97.5%下限 > 0、回収率（実際の払戻）> 100% |
| 凍結タグ | `forward-c-all` | `forward-cand2` |

* オッズは発走3分前のスナップショット（`python -m scrape snapshot` をタスクスケジューラで開催日に自動実行）。
* 合格しても、まず1点100円で3か月実戦し、数字が合うかを確かめてから賭け金を考えます。

## 全体の流れ
「① スクレイプ → ② データ準備 → ③ 学習 → ④ 検証 → ⑤ 実践」の順で、入口はそれぞれ1つです。

| 段階 | 入口 | やること | 出力 |
|---|---|---|---|
| ① スクレイプ | `python -m scrape weekly` | 結果・血統・ラップ・払戻・追い切り・オッズを取得し、欠損を補完 | `data/*.csv` |
| ② データ準備 | `python -m prep.ingest` → `python -m prep.features` | CSV を正規化・検査して取り込み、176列の特徴量を作る | `data/v2/*.parquet` |
| ③ 学習 | `python -m train --candidate <候補>` | 候補の設定どおりに本番用のモデルを学習して保存 | `models/v2/<候補>/` |
| ④ 検証 | `python -m evaluate --tag <名前> ...` | 2019〜2026年の前進検証で、変更を現行と同じレースで比べる | `data/v2/bench/` |
| ⑤ 実践 | `python -m predict --candidate <候補> --live` | 発走前の出馬表とオッズで買い目を出す（`--live` なし: 前向き検証の採点・判定） | `result/live/`・`result/v2/` |

## 実行手順
**準備**: `pip install -r requirements.txt`。スクリプトは `C:\Users\aassz\anaconda3\envs\keiba-ai\python.exe` で、リポジトリの直下から実行します。

**① ② 毎週（開催の翌週の月〜火）**
```bash
python -m scrape weekly          # 結果・血統・ラップ・払戻・追い切り・オッズの取得と欠損の補完
python -m prep.ingest            # CSV → data/v2/*.parquet（取り込みのたびにデータを検査）
python -m prep.fetch_patches     # ingest の WARN にレース情報の欠損・抜けレースが出たときだけ。その後もう一度 ingest
python -m prep.features          # 特徴量を作り直す
python -m pytest tests scrape/tests
python -m predict --candidate c_all   # ⑤ 前向き検証が何Rたまったか・途中の成績（候補2は --candidate cand2）
```

**開催日（自動）**: タスクスケジューラの `keiba-odds-snapshot` が毎日 8:00 から30分おきに `live/run_snapshot_hidden.vbs` を起動し、
開催日なら発走60〜1分前のオッズを `data/v2/odds_snapshots/` に取ります。開催日は PC の電源を切らないでください（スリープは可）。
手動で確かめるときは `python -m scrape snapshot --now --out-dir <作業用フォルダ>`。

**③ 学習**（候補を登録したときに1回。登録後は作り直さない）
```bash
python -m train --candidate cand2
```

**④ 検証**（モデルの変更を試すとき。2026-09-06 までのレースだけを使う）
```bash
python -m evaluate --tag current                              # 現行（C[all] と同じ作り方）
python -m evaluate --build-base base_pl3 --base-objective pl  # 年ごとの基礎モデルの予測を作る（1時間以上）
python -m evaluate --tag res_mkt --base base_pl3 --res-years 0 --half-life 730 --res-market --ref pl3_all_hl730
```

**⑤ 実践: 発走前の買い目**（開催日に。枠順は前日、天候・馬場は当日の朝、馬体重は発走の約70分前に出る）
```bash
python -m predict --candidate cand2 --live --watch    # 開催日の間ずっと、発走15分前になったレースから順に買い目を出す
python -m predict --candidate cand2 --live --within 20   # 発走まで20分以内のレースだけ1回
```
* 出馬表・今日終わったレースの結果・その時点のオッズを取り、学習と同じ関数で特徴量を作って、期待値1.3以上の単勝を出します（1回3〜4分）。
  結果は `result/live/` に保存。オッズは発走直前まで動くので、買う直前のオッズで期待値が変わる点に注意。
* 取れない項目（枠順・天候・馬場・馬体重・追い切り評価）は既定値で埋めずに警告します。警告が出たレースは学習時と条件がずれています。
* **まだ前向き検証の判定前なので、実際に賭けるかどうかは判定の後に決めます。**

**⑤ 前向き検証の判定**（1,000R たまったら候補ごとに1回だけ。2回目は実行されない）
```bash
python -m predict --candidate c_all --judge
python -m predict --candidate cand2 --judge
```

## 🔍 データ品質と検証
このプロジェクトで一番時間をかけたのは、モデルの改良ではなく**「測定値が正しいかどうかの検証」**です。見つけて直した主な不具合:

1. **払戻データの列ずれ** — `data/return_data_progress.csv` の約91%の行で列の順番がヘッダと違い、「3連複払戻」として馬単の払戻を読んでいた。
   旧システムの「回収率176.8%」はこの不具合によるもので撤回した（正しい払戻では80%前後）。
2. **偽レース** — db.netkeiba は存在しないレース番号に対して同じ日の1Rのページを返す。`python -m scrape results` はページのレースIDが違えば保存しない。
3. **レース情報の欠損** — 芝ダ・距離・天候・馬場が空欄のレースを `python -m scrape repair` で結果ページから補完（「不良」が「不」1文字で書かれる点も対応）。
4. **騎手・調教師IDの書式ゆれ** — 年によって `1170` と `01170` が混在。`prep/normalize.py` で5桁にそろえる。
5. **取り込み時の検査** — `prep/checks.py` が重複・欠損・オッズと払戻の食い違いなどを検査し、ERROR があれば保存しない。

## 旧システム（v1）
3連複を当てにいくシステム（LightGBM・Transformer・DAE・血統グラフ埋め込み・監督AI）でした。
2026年のテスト期間で3連複1点の回収率は約78%、実戦93レース（2026/7/18〜9/6）でも72.8%で、控除率並みでした。
モデルの評価が人気とほぼ同じで、市場に勝てている形跡はありませんでした。この結果から作り直したのが今のシステムです。

v1 のコードと説明は git タグ `v1-final` に残してあります（`git checkout v1-final`）。モデル・過去の予想・結果は `old/` にあります。
